## What this part of Peekaboo does

The phone signs people in through Supabase using Apple, Google, or the older username/password flow. Feature modules call the database directly; database rules decide whose profiles, messages, groups and private files can be read. Files are uploaded before their related rows are saved. Private files get temporary viewing links; profile and group pictures are public avatar files.

One-to-one and group chat add realtime updates, replies, reactions, photos/videos, voice notes, dares, pinned messages, read markers and search. Hidden-message rows remember Delete for me/Clear chat. Activity comes from a database function, while seen/cleared markers stay on the phone. The cleanup server removes old eligible media. Account deletion verifies the caller, optionally disconnects the matching Apple identity, removes that user's files and then deletes the auth account and its dependent rows.

## Integration change required by the fixes

Media tombstones prevent a deleted path from being reused while references or reports might race. `postFromStory` previously copied to a deterministic file name, so a rollback or deleted profile copy made later attempts reuse a tombstoned key. It now generates a new UUID for each copied file on every attempt while keeping its extension. The only `storage.copy` call in `src` was checked. Tests prove retry after failed insertion/cleanup and reposting a story after deleting its earlier copy.

Ordinary post, story, keep and Guess Who deletion removes the visible row first. If file removal is then denied to retain report evidence, that must not tell the person the content deletion failed. Those helpers now log cleanup failure after a successful row deletion and return success; a failed row deletion still throws and never attempts file removal. The eight regression checks cover both outcomes. This also means a storage outage can leave an owned file after the visible item is gone; it is a cleanup/integrity limitation, distinct from intentional evidence retention. Full account deletion continues to fail closed on file-removal errors.

Group reports now send `group_message` plus the offending message ID. The database agent verifies membership and records the real sender, preserving evidence for cleanup; the client type was extended to match.

## Limits and deployment notes

- No production migration, Edge Function deployment, app update or Git push was performed. Deploy database helpers first, then server functions, then the client when separately authorized. New helpers fail closed if absent.
- The Edge Functions run as real source in a local TypeScript/VM harness. Supabase, Apple fetches and signing helpers are test doubles; no real nonce exchange, Apple key, Google client configuration, provider JWT signature, hosted gateway or push delivery was validated here. Root integration tests separately exercise real local Postgres/PostgREST and JWT boundaries.
- Private signed URLs remain bearer links until their expiry. Immediate revocation needs a different download design. The in-app URL cache is now account-scoped, but previously copied links are not revoked.
- Storage and Auth are separate services. Account deletion retains the login after a storage error so it can be retried; files already removed remain removed. The account-deletion scope expires after ten minutes if the process is interrupted. Uploading from another device during deletion still needs explicit account-wide write blocking for a strict all-services guarantee.
- Failed cleanup or unknown upload outcomes can still leave private owned files. Rollback now handles known successful uploads, and account deletion can find owned anonymous orphans. A durable upload registry/garbage collector would cover process termination and prolonged outages.
- Current tracked source contained no service-role key, secret Supabase key, JWT credential or private key value. Public project IDs, Google web client IDs and download links are expected public configuration. This does not audit every historical commit or external account setting.
- Public-content word filtering remains mainly in the client; direct API writes can bypass that moderation layer. Database access and length rules still apply. Search treats an underscore in a username as an ILIKE wildcard; low severity.
- Physical camera, Apple/Google prompts, face tracking, microphone, Photos permissions, native map rendering, slow mobile hardware and real notification behavior still require device testing. No test count here claims exhaustive native coverage.
