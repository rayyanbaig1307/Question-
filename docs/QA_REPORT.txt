WHAT THE APP DOES AND HOW DATA MOVES

Peekaboo is a camera-first social phone app. Friends can share profile posts,
24-hour stories and disappearing peeks; send direct/group text, voice, media,
replies and reactions; pin/search/hide messages; and receive Inbox activity.
It includes daily dares, drops, chat dares, forfeits, Guess Who, hit ups, groups,
close friends, private accounts, blocking/reporting, Keeps, profile songs and an
optional friend map. A separate static website hosts help and legal pages.

The frontend is Expo/React Native with TypeScript and Expo Router. Screens call
feature modules in src/lib. Those modules mostly talk directly to Supabase:
Auth verifies the session, Postgres stores content and relationships, row-level
security (RLS) controls access, Storage holds files, and Realtime updates chats.
Apple/Google sign-in gives Supabase a provider token. Older accounts use email
or username/password. The app has no separate general-purpose application server.

Three Edge Functions handle username authentication, account deletion and media
cleanup. Trusted SQL functions handle social actions and security checks. Database
triggers queue notifications; phone-local jobs schedule drop alerts. Apple supplies
song search. Camera/gallery -> editor -> destination/audience -> file upload ->
database write is the main sharing path. An authorized reader queries the row,
requests a temporary private file link, then displays it. Avatar files are public.
Files and database writes are separate operations, so rollback/retry behavior and
partial failures matter. Already issued media links remain bearer links until
their expiry; changing database permissions cannot revoke a copied URL instantly.

REMAINING ISSUES AND HONEST LIMITS

OPEN-01 — MEDIUM — Public-name moderation can be bypassed via direct HTTP.
Reproduce in the local test fixture: PATCH your own profile username to f.u.c.k.
The API returns 204 although the normal UI rejects it. The database validates
format/length but does not enforce the nuanced client word policy. Fix: put the
same public-name/public-text policy at a trusted write boundary, preserving real
name and private-chat exceptions. This needs a shared product policy; it was not
silently replaced with a crude SQL denylist. This is not an access-control bypass.
[Update 2026-11-04: FIXED – see INTEGRATION UPDATE.]

OPEN-02 — MEDIUM — Signed-in web app crashes in the native pager.
Reproduce (on the original code): build the browser fixture and open the
signed-in settings page in the web build. It raised codegenNativeCommands is not
a function before the private page loaded. (The QA_FULL_WEB switch this report
used to reproduce it has been removed.) Fix: add a web-safe pager
implementation or explicitly declare the phone app native-only and test the
equivalent native flow on devices.
The public website and logged-out browser screens pass. This finding does not
prove a native build launch crash.
[Update 2026-11-04: FIXED with a web pager; no browser case is skipped now –
see INTEGRATION UPDATE.]

OPEN-03 — MEDIUM — A completely fresh hosted setup has an owner-row assumption.
The historical report-alert migration expects an existing owner profile, while
the old README instructed running only the first schema. Fix for a future setup:
make that owner/report configuration explicit and idempotent, then apply the full
migration history in a disposable full Supabase instance. This is not a claim
that a fresh hosted installation was validated.
[Update 2026-11-04: FIXED. The migration now adds the owner only if that
profile exists, and the local test fixture has no owner row at all (the
earlier made-up owner row is gone). On a fresh database the owner adds
themselves by hand; see README.md and the INTEGRATION UPDATE.]

OPEN-04 — MEDIUM dependency findings remain in Expo/build tooling chains.
Reproduce: npm ci; npm audit. See the saved audit JSON for affected versions and
chains. Fix: take upstream compatible updates and recheck Expo native versions;
avoid force-upgrading core native packages across SDK versions. Zero high or
critical advisories remain. No exploit of these moderate entries was demonstrated.
[Update 2026-11-04: MOSTLY FIXED with scoped overrides – see INTEGRATION UPDATE.]

OPEN-05 — LOW — Username ILIKE treats underscore as a one-character wildcard.
Reproduce the documented username availability/auth lookup with an underscore

[Update 2026-11-04: FIXED in friend search – see INTEGRATION UPDATE.]

API AND LIBRARY FINDINGS

R2-API-01 — CRITICAL — FIXED
What broke / reproduce: A native Delete forever confirmation for account A can survive logout/unmount. If B signs in before its callback runs, the old client helper reads B's current session and deletes B. Changing accounts while the Apple confirmation is open has the same risk.
Fix and proof: The screen passes the account that opened the confirmation; the helper checks it before and after Apple and sends expected_user_id. The server compares that ID with the verified JWT subject before Apple calls, deletion scope or file removal. Wrong type returns 400; mismatch returns 409. Tests cover stale A→B callbacks, a switch during Apple, and a switch at the server boundary. Frontend native-alert tests separately cover the actual confirmation lifetime.

R2-API-02 — HIGH — FIXED
What broke / reproduce: The Apple code was not tied to the account being deleted. Deleting A while supplying an authorization code for Apple identity B caused the handler to send B's token for revocation. A password-only account could also submit somebody else's code.
Fix and proof: Compare the subject of the token returned directly by Apple's HTTPS token endpoint with the Apple identities Supabase verified for the caller. A mismatching Apple ID is never revoked; the Apple disconnect is skipped and the verified caller's own account is still deleted. A code from an account with no Apple login is never sent to Apple, and that account is still deleted. Tests verify mismatching and matching identities, ignored request-body identity claims, password-only callers and linked Apple accounts.
[Update 2026-11-04: the first version rejected a mismatch before deletion, which stopped real owners whose iPhone uses another Apple ID; it was changed as described above.]

R2-API-03 — HIGH — FIXED
What broke / reproduce: Username throttling still counted first and logged later. A burst of 100 wrong passwords reached 100 credential checks despite an eight-try limit; 30 parallel signups exceeded the five-account limit. Database failures removed the protection.
Fix and proof: Reserve attempts atomically through a service-only SQL function before credential checks, and fail closed when it is unavailable. Handler tests allow 8/reject 92 logins and allow 5/reject 25 signups. Database tests independently verify the actual SQL locking and permissions. The limit now counts reserved tries, including successful ones.
[Update 2026-11-04: tries are still reserved first, but a correct login or a server problem now gives its try back, and the limits are per username and address, per username and per address – see INTEGRATION UPDATE.]

R2-API-04 — HIGH — FIXED
What broke / reproduce: Account deletion ignored storage/query failures, skipped files after the first 1,000 entries or anonymous-post rows, and missed anonymous uploads whose row had already been removed.
Fix and proof: Page every list, include owner-attributed orphaned anonymous uploads through a service-only helper, stop on errors and keep the login retryable. The verified user's short deletion scope lets intentional account deletion proceed despite temporary cleanup-retention claims, without allowing another user's files to be removed. Tests cover pagination, nested folders, each outage, invalid tokens, victim IDs in the body, ownership and scope failure.

R2-API-05 — HIGH — FIXED
What broke / reproduce: Cleanup of an old shared peek treated a failed recipient query as an empty conversation and deleted a file another recipient still needed. Filtering hidden rows could cause the same mistake. A safe main file could also have a poster/overlay reused by another live or saved message. Group-message deletion removed shared companion files without checking.
Fix and proof: A privileged SQL helper checks all references, including hidden rows, groups and reports. Every distinct main/poster/overlay path must receive a positive claim before any file is removed; one failure or live reference stops the bundle. Storage rechecks under the shared path lock. Tests cover unopened/saved recipients, query failure, safe cleanup, shared companions, failed overlay checks, group reuse and duplicate paths.

R2-API-06 — HIGH — FIXED
What broke / reproduce: Signed private links remained cached across users. B could receive A's cached private keep URL without a new permission check; an old signing response could refill the cache after switching.
Fix and proof: Clear on identity changes, discard older replies and key mounted-hook results to the current identity version and requested paths. Tests cover logout, switching, delayed responses and a real mounted hook. Previously copied bearer URLs remain valid until expiry; this fix cannot revoke them.

R2-API-07 — HIGH — FIXED
What broke / reproduce: A crafted video PNG note with frames:["not-a-frame"], null rows or invalid coordinates was accepted, then crashed the animation's .map call. Huge advertised note lengths caused unnecessary requests.
Fix and proof: Validate the whole note, finite numbers, dimensions, 151 frames, four faces and a 128 KB limit. Hostile metadata is rejected; legitimate animation/interpolation remains valid.

R2-API-08 — HIGH — FIXED
What broke / reproduce: Two mounted copies of a direct chat reused a realtime channel name. Adding the second listener after subscription can throw, repeating the documented launch-crash failure pattern.
Fix and proof: Give every direct-message listener a unique suffix. A model of the actual subscribed-channel restriction reproduces the old throw; duplicate chat, group and reaction subscriptions now succeed and clean up separately. This is not a hosted websocket load test.

R2-API-09 — HIGH — FIXED
What broke / reproduce: Old native Block/report callbacks could run after A's screen unmounted and act through B's global session. A delayed success could navigate or show another prompt in B. An old logout callback could also sign B out after waiting for push cleanup.
Fix and proof: Cancel stale hook continuations. Block calls carry A to a server-checked overload; reports include A's reporter ID so row security rejects a shifted JWT. Logout verifies identity before and after the asynchronous push step and preserves a newer login event. Tests cover callback lifetime, delayed prompts/responses, approving-user payloads and the logout race.

R2-API-10 — HIGH — FIXED
What broke / reproduce: Scheduled cleanup's old candidate snapshot omitted group-message references and could race a new report/reference. Its handler also returned success after Storage failures.
Fix and proof: The database agent added claims, path locks, deletion guards and tombstones; the handler calls the claim helper and returns a retryable 503 with its partial count on failure. Tests cover secret rejection, Vault/candidate/Storage failures, 250-file batching, partial results and unexpected rejection. The database/native/REST suites own actual group/reference/report race proof.

R2-API-11 — MEDIUM — FIXED
What broke / reproduce: Username auth crashed on JSON null, coerced nonstring passwords and read huge bodies. Apple revocation could hang forever.
Fix and proof: Bound auth/delete request bodies, validate types, reject huge Apple codes and abort Apple calls after ten seconds. A stalled Apple service no longer prevents the user's deletion indefinitely. Original Apple revocation was best effort; missing secrets/provider failure still skip that external step and are a deployment limitation.

R2-API-12 — MEDIUM — FIXED
What broke / reproduce: The initial saved-login reply could overwrite a newer logout; signout errors and saved-login read failures were mishandled.
Fix and proof: Ignore stale initial replies, handle returned errors and clear only the intended local account. Real React-provider tests verify the failure and race paths. Stale UI state was reproduced; this was not a demonstrated server-side token bypass.

R2-API-13 — MEDIUM — FIXED
What broke / reproduce: Apple/Google names were assigned after the session could open setup. A second Apple account without a new name inherited the prior user's name.
Fix and proof: Set or clear the name before opening the session, and clear it on failed auth. Tests exercise name timing, account changes, cancellation, missing tokens, native fallbacks and the hashed/raw nonce pairing.

R2-API-14 — HIGH — FIXED
What broke / reproduce: A delayed Activity refresh for A overwrote B's activity when the hook stayed mounted. Within one account, an old refresh replaced newer items and a delayed local preference read undid Clear.
Fix and proof: Account-keyed data, request versions and preference-action versions discard stale replies. All three original behavioral regressions fail and all three changed checks pass. The root navigator also remounts private screens by account.

R2-API-15 — MEDIUM — FIXED
What broke / reproduce: Hidden-message lookup failed open, so cleared messages reappeared during a privacy-table outage. The client-side ID list alone was also bounded.
Fix and proof: Read errors now stop the request. The database agent enforces hides in row security for direct reads, search and reactions, so the client list is no longer the privacy boundary.

R2-API-16 — MEDIUM — FIXED
What broke / reproduce: Failed multi-file video uploads left earlier files behind; a failed group-photo save left its new public avatar upload behind.
Fix and proof: Roll back known successful files, retain the original error if cleanup also fails, and remove rejected group-photo uploads. Tests cover all six media folders, later-file failures, cleanup failure, first-file failure and success.

R2-API-17 — MEDIUM — FIXED
What broke / reproduce: Profile song data could carry file/javascript/intent links or a phishing host under the Apple Music label. Music searches had no deadline.
Fix and proof: Restrict song URLs to HTTPS Apple/mzstatic hosts and abort searches after 15 seconds. Tests cover unsafe links, normal results, special-character search encoding, empty queries, failure and a stalled service.

R2-API-18 — HIGH — FIXED
What broke / reproduce: Reported media protection depended on the content row still existing. After a report, an author could delete the post/story/message row and then remove its file: the retention join no longer found the reported row.
Fix and proof: The database agent reproduced the loss and added private, persistent report-to-file snapshots under the same path locks. The file remains protected after the visible content row is removed. Existing reachable reports are backfilled; already lost bytes cannot be recovered. Targeted database tests reject deletion of the evidence while still allowing explicitly scoped full account deletion.

FRONTEND FINDINGS

FE-01 — HIGH — FIXED
What broke / reproduce: Start a dare, drop or forfeit photo; also select My Story; turn on Close friends only; confirm the story preview. The story was restricted, but the same photo became a profile post with the default everyone audience. A public account could expose the restricted photo to strangers.
Fix and proof: Pass the selected audience to every generated post, and show the privacy switch for special posts even without a story. Three rendered screen cases fail on the original and pass after the fix (share.test.cjs).

FE-02 — HIGH — FIXED
What broke / reproduce: Start showing your location while the permission prompt is delayed, then choose Hide. Complete the older permission prompt. The old request switched sharing back on. A delayed profile save could do the same; an old GPS lookup could upload coordinates after Hide.
Fix and proof: Keep profile writes in order, discard superseded permission/GPS results, and cancel background refresh work when its effect ends. Hiding does not wait for GPS. The original fails all three controlled timing cases; all pass after the fix (location.test.cjs).

FE-03 — HIGH — FIXED
What broke / reproduce: In Settings, switch Private account off then on while the first save is delayed. The older public save could finish last and leave the account public. Similarly, choose Friends of friends then Nobody for hit ups; the older, broader choice could win.
Fix and proof: Queue privacy saves in the order selected. Merge only the changed profile fields so an unrelated late response cannot overwrite other local settings. Both original timing tests fail; both pass now (settings.test.cjs).

FE-04 — HIGH — FIXED
What broke / reproduce: In Close friends, start with Bob excluded. Add Bob and then remove him before the first request finishes. Let the removal finish first and the older addition finish last. The screen said Bob was excluded while the saved list still included him.
Fix and proof: Allow only one pending change per person; disable that person's row until the save settles. A failed save restores the old choice. The original privacy invariant fails (true stored versus false shown); the fixed tests pass (privacy.test.cjs).

FE-05 — HIGH, CONDITIONAL — FIXED
What broke / reproduce: Replace account A's signed-in session directly with account B's session without an intermediate signed-out state. The navigation tree kept its identity, so old chats, forms and component state could remain until new loads completed. The ordinary Log out then Log in path already unmounted it.
Fix and proof: Give the navigation tree a key based on the signed-in user ID. The rendered test proves it now remounts on account change (navigation.test.cjs). Combine with the separate signed-media cache/auth fixes; this is a device state isolation issue, not a database authorization bypass.

FE-06 — MEDIUM — FIXED
What broke / reproduce: Press Send twice before the first render disables it. Share sent two identical peeks; the direct chat, group chat and editor-to-group paths also sent duplicates. Delayed preview callbacks could use an old completion snapshot.
Fix and proof: Use immediate in-flight locks and a live completion record where a send has several destinations. Retrying after a later destination fails still avoids resending successful destinations.
